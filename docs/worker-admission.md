# Durable Worker admission and execution observation

## Implemented local boundary

`worker/src/freechat_worker/execution.py` implements `DurableExecutionDriver`, usable
through the existing `LocalRequestExecutionService` driver interface. It is **not** a
vLLM adapter, HTTP server, engine launcher or automatically enabled Worker runtime.
The complete pinned fork is now available on ross at `third_party/vllm`.
Three-protocol request admission and EngineCore cancellation/completion are still
integration gates, not missing-source blockers. Follow section 0 of the root plan.

The implementation reuses standard-library SQLite (WAL, synchronous FULL) for a
small Worker-local identity journal. It does not add a control-plane database or store
prompts, model outputs, tokens, credentials or KV tensors. One file belongs to one
Worker generation and engine instance. An OS file lock rejects competing owners,
including access through a symbolic link. Per-decision asynchronous locks serialize
admission and cancellation without waiting on unrelated requests' backend operations.

All engine ingress must call `admit()` using authenticated Scheduler identity, and
must not expose an alternate inference endpoint that bypasses the gate. Calling this
Python method does not authenticate identity. Gateway internal headers alone are not
sufficient; public client fields must never create trusted execution commands.

## State and failure behavior

| Event | Durable state before side effect | Release behavior |
|---|---|---|
| QUERY before arrival | Identity and sequence, admission open | UNKNOWN, capacity held |
| ABORT before arrival | Closed tombstone; no dispatch ever issued | NOT_ACCEPTED can release |
| First admission | Closed to duplicate admission; dispatch intent recorded | No release proof |
| Submit timeout, cancellation or lost acknowledgement | Dispatch remains uncertain, never automatically resubmitted | Query/abort, capacity held |
| ABORT after dispatch | Cancel intent recorded before sending signal | Signal alone cannot release |
| Backend absence after dispatch | Not converted into NOT_ACCEPTED proof | UNKNOWN, capacity held |
| Completed/aborted execution with pending submit retry | No terminal proof persisted | Capacity held |
| Completed/aborted, quiescent, submission-fenced | Terminal proof and incremented sequence in one SQLite transaction | Matching receipt can release |
| Worker journal restart | Same incarnation, identities, tombstones and sequence | Never reset numbering or replay submissions |

Decision IDs are unique within a tenant. Reusing a decision with a different request
binding is rejected. Engine request IDs include Worker incarnation and tenant/decision
identity. A changed Worker generation or engine instance cannot open the same journal.
The driver validates backend request identity and an aware observation timestamp no
more than five seconds old. Terminal proofs are retained; subsequent queries refresh
the receipt timestamp/sequence without reopening or repeating backend execution.

The backend's `submission_fenced` assertion is separate from queue emptiness and
`quiescent`. It must account for in-flight RPC delivery, retries and **all** child
requests generated by the protocol/engine. An async abort method returning or a
frontend output iterator ending does not establish either assertion. A backend
adapter that reports these incorrectly invalidates release safety.

Every new receipt gets a durable increasing observation sequence before it is returned.
Lost acknowledgement can cause a sequence gap, not reuse. Storage failure never
returns an uncommitted release proof. A persisted cancel intent also causes subsequent
QUERY reconciliation to retry abort delivery. Per-request operations must remain
cancellable; deadlines are supplied by the caller (the existing reconciler uses two
seconds). The driver does not create unbounded detached submit/abort tasks.

## Local operational limits

- Explicit `create=True` is for initial provisioning of a missing journal. Existing
  empty/corrupt journals are not silently initialized, even with this flag. Normal
  restarts require the existing database; missing storage requires operator recovery.
- Default maximum is 10,000 identities, including pre-arrival queries and tombstones;
  canonical identities are limited to 8 KiB. Full storage rejects new identities.
  Tombstones are not evicted to make space. Existing observations can still progress.
- Keep the database, WAL and owner path together on a local, private, persistent
  filesystem. Do not unlink/replace files while active, copy a live database without
  SQLite backup coordination, mount it on a distributed filesystem, or use hard-link
  aliases. Protect this directory with the Worker service account's permissions.
- One event loop, one local owner and one engine incarnation only. This is not a
  multi-host leadership fence or storage failover design. Owner-lock release does not
  prove the engine stopped. `close()` rejects in-flight operations and does not stop
  any submitted execution.
- Database transactions are small but synchronous. No throughput/latency benefit is
  claimed; event-loop disk latency and journal compaction need profiling/design before
  production use. Sequence/tombstone compaction must not reopen old request identities.
- This is an at-most-one **local dispatch attempt** gate, not exactly-once inference
  or exactly-once event delivery. Uncertain dispatch may hold capacity indefinitely
  until a trustworthy backend observation or explicit operator recovery is available.

## Evidence and next integration gates

`evidence/worker-admission/20260920/` contains full CPU regression results, coverage,
quality logs and source/artifact hashes. Tests exercise duplicate admission, identity
and time fences, races, bounded storage, before/after-commit failures, lost submit
acknowledgement, abrupt child process exit with no cleanup, and journal reopening.
One test starts an actual local Python process and requires its exit before release;
that process performs no inference and proves nothing about CUDA stream completion.
Loopback gRPC tests join this journal to the real Scheduler reservation/reconciliation
code; engine observations in those tests remain deterministic CPU fixtures.

Required before enabling the default Worker path:

1. Use the restored complete pinned fork on ross and attach trusted ingress for
   Chat Completions, Responses and Anthropic Messages. Bind every engine-created child
   ID to the immutable route; reject retries and bypass ingress consistently.
2. Implement `ExecutionBackend` using actual engine acceptance, abort and completion
   acknowledgements. Prove absence of pending submissions, child requests and GPU work
   rather than synthesizing quiescence from HTTP EOF or a cache-free event.
3. Wire persistent journal ownership/lifecycle into the real Worker launcher and
   authenticated runtime service; retain local-only defaults until this is validated.
4. Join confirmed execution identities to per-rank request/cache/transfer budgets,
   including restart and uncertain-dispatch reconciliation.
5. Complete local dependency process fault tests and separately authorized GPU/Harness
   acceptance. No H100, physical abort, performance, RTO or HA claim is established here.
